# Kiwi-Vue

Kiwi-Vue is the Vue 3 companion library of the Kiwi Server Framework: typed API bindings for the generic entity and
report endpoints, reactive loading state, structured error handling, and utilities. This skill describes Kiwi-Vue
**2.x**, which works with **Kiwi-Server 1.5** (Kiwi-Vue 1.x works with Kiwi-Server 1.4 only).

The documentation is in `references/` (paths relative to this skill's base directory):

- `references/README.md`: the complete library documentation, with all APIs and options. Read the section you need
  before writing non-trivial code.
- `references/CHANGELOG.md`: changes per release, including the migration guide from 1.x.
- `../kiwi-server/references/`: the server documentation, if the backend matters: generic endpoints, filters and error
  responses in `06-web-mvc-endpoints.md`, the TypeScript code generation in `07-testing.md` ("Frontend
  Code-Generation"), filter operators and reports in `04-querying-access-control.md`.

If the project still uses Kiwi-Vue 1.x (`"@werdenktwas/kiwi-vue": "^1…"` in `package.json`, `update<PUT, R>(…)`
calls, services with two type parameters), the examples here won't compile there, and a 1.x client can't talk to a
Kiwi-Server 1.5 backend (`PUT` updates were removed). Tell the user, and suggest the `/kiwi:kiwi-upgrade` skill.

## Modules

| Import path                        | Contents                                                                    |
|------------------------------------|-----------------------------------------------------------------------------|
| `@werdenktwas/kiwi-vue/api`        | Models and errors: `ApiError`, credentials, `IPage`, `columnFilter`, `Sort` |
| `@werdenktwas/kiwi-vue/services`   | `provideApi`/`createApi`, `basicCrudService`, error handler, `useLoading`   |
| `@werdenktwas/kiwi-vue/components` | `<Loading>`, `<ErrorBoundary>`                                              |
| `@werdenktwas/kiwi-vue/utils`      | `Compare`/`sorting`, validations, `loadAllPages`, `deferPromise`, `delay`   |

Import from the sub-paths, as above. The root path only re-exports them as namespaces (`ServicesModule`, …).

## How a Kiwi-Vue frontend is put together

1. **Types are generated by the server.** Kiwi-Server's `TypescriptFieldsetSourceRenderer` generates a `*.model.ts`
   module with nominal ID types (`TodoItemId`), one interface per fieldset (`ITodoItemDefault`, `ITodoItemShort`), and
   the request bodies of the create and update commands (`ICreateTodoItem`, `IUpdateTodoItem`). Use them instead of
   writing entity interfaces by hand, and regenerate them when the server's schemas, fieldsets or commands change (see
   `../kiwi-server/references/07-testing.md`). Don't edit the generated file.
2. **One API client per application**, provided at the root component:

   ```ts
   import { provideApi } from '@werdenktwas/kiwi-vue/services'
   import { type ApiCredentials, missingCredentials } from '@werdenktwas/kiwi-vue/api'

   const credentials = ref<ApiCredentials>(missingCredentials) // replaced after login
   provideApi({ apiUrl: import.meta.env.VITE_API_URL, credentials })
   ```

   `credentials` is reactive and evaluated per request, so a login only replaces its value (e.g. with
   `new JwtBearerToken(token)` or `new UsernamePassword(user, password)`). Outside of components (stores, router
   guards), create the client with `createApi(options)` and pass the same instance to `provideApi`.
3. **One service class per entity**, extending the generated base class with the generated types:

   ```ts
   import { basicCrudService } from '@werdenktwas/kiwi-vue/services'
   import type { ICreateTodoItem, ITodoItemDefault, IUpdateTodoItem, TodoItemId } from '@/api/demo.model'

   export class TodoItemService extends basicCrudService<ITodoItem, TodoItemId, ICreateTodoItem, IUpdateTodoItem>(
     'TodoItem', // entity name of the generic endpoints: GET/POST /TodoItem, GET/PATCH/DELETE /TodoItem/{id}
   ) {}
   ```

   In components, instantiate it with `useApiService(TodoItemService)` (requires the injection context of `setup`);
   elsewhere with `new TodoItemService(api)`. Add custom endpoints as methods using `this.api.request(…)` and
   `unwrapResponseJson`, with paths relative to the API URL.
4. **Errors are handled centrally**: `provideApiErrorHandler({ transform, consumers })` near the root, and
   `errorHandler.wrapService(service)` for services whose errors should be shown to the user (e.g. as toast), instead
   of `try`/`catch` at every call site.
5. **Asynchronous state** goes through `useLoading<T>()` and is rendered with `<Loading :state>`, not with ad-hoc
   `loading`/`error` refs.

## Working with the generic endpoints

- **Fieldsets**: `findById(id, { fieldset: 'short' })` and `findPage({ fieldset })` return the fields of that
  fieldset. Their result type parameter must extend the service's entity type `T`
  (`findPage<S extends T>(…)`): a fieldset interface that isn't a subtype of `T` (`ITodoItemShort` lacks fields of
  `ITodoItemDefault`) doesn't type-check. For services used with several fieldsets, use the schema interface
  (`ITodoItem`, all fields optional) as `T`, and request each fieldset with its interface:
  `findPage<ITodoItemShort>({ fieldset: 'short' })`.
- **Paging and sorting**: `findPage({ pageSize, pageNumber, sort: [{ field: 'title', direction: 'asc' }] })` returns
  an `IPage<T>`. The server caps the page size; use `loadAllPages(…)` (from `utils`) to load everything, with a sort
  order that is unique per item.
- **Filters**: `filter` takes the properties of the entity's query filter class (`{ titleLike: 'milk' }`) and column
  filters created by `columnFilter(column, operator, values)` (from `api`), which escapes commas and backslashes. Don't
  build `column:operator=value` strings by hand.
- **Creating**: send the body typed by `ICreate…`. Required properties are non-optional in the generated interface.
- **Updating is a partial `PATCH`**: send only the properties that changed. Absent properties are left unchanged,
  `null` clears a nullable property, and unknown properties (e.g. `id`, or fields the update command doesn't declare)
  are rejected. Build the body from the form's changed fields typed as `IUpdate…`, not by spreading the loaded entity.
- **JSON keys are the server's body property keys**: for references they are the relation's schema field name (e.g.
  `list: listId`), not necessarily the column name used in fieldsets (`listId`). The generated interfaces have the
  right keys.
- **Metadata**: `fetchMetadata()` returns the entity's fieldsets, columns, filter properties and command body
  properties (`required`), e.g. for generic tables or forms.
- **Reports**: `basicReportService('<entity>')` queries `GET /<entity>/_report` with dimensions, metrics, slices and
  sort; the resulting `AnalyticalReport` has helpers like `groupBy`, `pivot` and `aggregate`.
- **Aborting**: every service method accepts `{ signal }`. Combine it with `load(promise, { abort })` so a newer load
  cancels the outdated request.

## Errors

Failed requests reject with `ApiError` (`code`, `details`, `status`, `errorType`, nested `errors`). Notable codes:

| Code                                      | When                                                                                             |
|-------------------------------------------|--------------------------------------------------------------------------------------------------|
| `entity-body-invalid`                     | Invalid create/update body; `errors` has one entry per field (`details.fieldName`)               |
| `entity-field-missing-value`, `…-invalid` | Nested field errors of `entity-body-invalid` (also `entity-field-unknown`, `…-mismatched-input`) |
| `entity-not-found`                        | `404` (`findById` resolves `null` instead, `requireById` rejects with `EntityNotFound`)          |
| `access-denied` / `forbidden`             | `403` (`ForbiddenError`), with the server's code if the response had a body                      |
| `unauthorized`                            | `401` (`UnauthorizedError`)                                                                      |
| `http-error`, `response-not-json`         | Error response without body; success response that isn't JSON (e.g. proxy HTML page)             |

User-facing messages come from an error transformer: `i18nErrorTransformer({ tm, rt, messagesKey })` with vue-i18n,
or `resourceErrorTransformer({...})` without. Message keys are `code` or `code[detail=value,…]`, e.g.
`"entity-field-missing-value[fieldName=title]": "Please enter a title."`. The `entityType` detail is the fully
qualified Kotlin class name. Without a message for `entity-body-invalid`, the messages of its nested errors are shown,
one per line. Add messages for the codes the backend actually throws (its `DomainException` codes), plus
`access-denied`, `forbidden` and `unauthorized`.

## Pitfalls

- **Request paths are relative to the API URL**, also with a leading slash: `/TodoItem` with the API URL
  `https://host/api/` requests `https://host/api/TodoItem`. Pass a `URL` for anything outside the API.
- **`useApi`, `useApiService` and `useApiErrorHandler` need a component's `setup` context** (they use `inject`);
  calling them in a store or after an `await` in `setup` fails. Use `createApi` and plain constructors there.
  (`useLoading` has no such restriction.)
- **`JwtBearerToken` doesn't refresh tokens**: once `isValid()` is false, requests reject with `CredentialsInvalid`.
  Replace the credentials ref after refreshing, and handle `UnauthorizedError` (e.g. redirect to login). Kiwi-Server
  1.5 validates tokens via the application's Spring Security setup; the client only sends them.
- **Loading state**: only the latest `load` updates the state; `load(promise, false)` keeps the current state while
  refreshing in the background; `emplace(value)` sets a known result. Read results via `resultOrNull`/`resultOrElse`
  instead of inspecting `state` by hand.
- **Error handler without provider**: `useApiErrorHandler()` falls back to a handler that only logs a console warning,
  so the user never sees the error. Provide one at the root.
- **`<Loading>`/`<ErrorBoundary>` without imports** need `KiwiResolver()` in the `Components({ resolvers })` plugin of
  `vite.config.ts`.
- **Validation rules** return `true` or a message string (`ValidationRule<T>`); `Validation<T>` is a factory taking the
  message: `isNotBlank('Required')`. Server-side validation still applies, show its `entity-field-invalid` errors too.

## Working style

- Read the existing services, stores and error messages of the project first, and follow their conventions.
- Check the backend's generated model file and command declarations before sending new properties: a key the server
  doesn't declare fails the whole request.
- After changes, run the project's type check and tests (`vue-tsc`, `npm test`/`vitest`); if they can't run, say so.
